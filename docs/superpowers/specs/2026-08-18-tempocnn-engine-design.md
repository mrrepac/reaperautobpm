# Замена движка на TempoCNN

Дата: 2026-08-18
Статус: дизайн, к реализации

## Контекст

Текущий движок (v1.3.0) — Essentia RhythmExtractor2013 / BeatTrackerMultiFeature,
статический Windows-экзешник `essentia_streaming_rhythmextractor_multifeature.exe`.
Работает, но точность и устойчивость к ошибкам метрического уровня (half/double-time)
хочется улучшить.

TempoCNN (Hendrik Schreiber, Meinard Müller — ISMIR 2018, "A Single-Step Approach to
Musical Tempo Estimation Using a Convolutional Neural Network") известен лучшей
устойчивостью именно к октавным ошибкам темпа по сравнению с классическими бит-трекерами.

## Решение

TempoCNN **заменяет** Essentia целиком, а не дополняет его вторым мнением. Поток
действия (метаданные → движок → диалог подтверждения) не меняется — меняется только
то, что стоит на месте движка.

### Модель

`deeptemp_k16` — модель общего назначения из репозитория `hendriks73/tempo-cnn`,
без жанровой специализации (в отличие от `dt_maz_*` / `fma2018*`, обученных под
конкретный материал).

### Почему не готовый tempo-cnn как есть

Оригинальный пакет `tempocnn` — Python + TensorFlow/Keras (`pip install tempocnn`,
CLI `tempo -i file.wav`). Готового portable-экзешника нет. Прямая упаковка через
PyInstaller с полным TensorFlow превратила бы движок из ~24 МБ в ориентировочно
400–800 МБ и заметно замедлила бы запуск — несовместимо с духом проекта
(лёгкий, самодостаточный `engine/`, никакого локального Python-окружения от
пользователя).

### Архитектура нового движка

1. **Конвертация модели (разово, на этапе разработки, не в рантайме пользователя).**
   Веса `deeptemp_k16` (Keras `.h5`) конвертируются в ONNX через `tf2onnx` на машине
   с установленными `tempocnn`+`tf2onnx`. Результат сверяется с оригинальным
   Keras-инференсом на наборе тестовых треков — BPM должен совпадать в пределах
   погрешности округления. Файл `deeptemp_k16.onnx` (несколько МБ) коммитится в
   `engine/`, SHA-256 фиксируется в README, как сейчас для Essentia-бинарника.

2. **Runtime-движок** — Python-скрипт, упакованный `PyInstaller --onefile` в
   `tempocnn_engine.exe`:
   - извлечение признаков (мел-спектрограмма, 11025 Hz) — код из `tempo-cnn`
     переиспользуется как есть, не переписывается заново, чтобы не разойтись
     численно с оригиналом;
   - инференс — `onnxruntime` вместо `TensorFlow`/`Keras`;
   - ожидаемый размер — десятки МБ (`onnxruntime` + `librosa`/`numpy`/`scipy`),
     на порядок легче варианта с полным TensorFlow, хоть и тяжелее чистого
     C++ Essentia-бинарника.

3. **PowerShell-обвязка.** `launch_essentia.ps1`/`run_essentia.ps1` →
   `launch_engine.ps1`/`run_engine.ps1`, параметризованные под новый `.exe`.
   Контракт запуска не меняется: асинхронный процесс, файл-результат,
   таймаут 180 с (`ANALYSIS_TIMEOUT_MS`), результат в `engine/bpm_result_<guid>.txt`.

### Контракт вывода

У TempoCNN нет прямого аналога "ticks detection confidence" из BeatTrackerMultiFeature —
вместо неё softmax-вероятность по классам темпа. Новый формат stdout движка:

```text
__ENGINE_EXIT__=0
bpm: 139.93
confidence: 0.842
```

`confidence` — вероятность максимального класса, диапазон 0–1 (раньше было
0–~3 у Essentia). `parse_essentia_output` в Lua-скрипте переименовывается и
адаптируется под новый маркер и новую шкалу; заголовок диалога подтверждения
меняет `conf 2.70` на `conf 0.84` — семантика другая, формат тот же.
Ошибки движка (битый файл, слишком короткое аудио, повреждённая ONNX-модель) —
тем же путём: ненулевой exit code плюс текст ошибки в stdout.

### Выкатка

- `essentia_streaming_rhythmextractor_multifeature.exe` и его SHA-256 из README
  убираются полностью.
- `THIRD_PARTY_NOTICES.md`: запись про Essentia заменяется записью про `tempo-cnn`

## Что отвергнуто

**Второе мнение в диалоге (Essentia + TempoCNN одновременно).** Усложняет UI и
увеличивает время анализа (два движка вместо одного) ради выгоды, которая не была
целью запроса — цель "заменить", не "сверить".

**Essentia со сборкой essentia-tensorflow (`TensorflowPredictTempoCNN`).** Требует
пересборки самой Essentia с поддержкой TensorFlow — тяжелее, чем взять оригинальный
`tempo-cnn` и заменить в нём только инференс на ONNX. К тому же официальные модели
для этого пути (с essentia.upf.edu/models) лицензированы MTG под CC BY-NC-SA 4.0 —
некоммерческая лицензия, хуже подходящая для плагина, который люди потенциально
используют в коммерческой работе. Модели из оригинального репозитория Schreiber —
AGPLv3, без ограничения на некоммерческое использование.

**PyInstaller с полным TensorFlow вместо ONNX.** Проще в реализации (берёшь
`tempocnn` как есть), но раздувает движок до сотен МБ и заметно увеличивает
время запуска — не соответствует текущему масштабу проекта.

## Открытые риски

- Точность конвертации Keras → ONNX проверяется вручную на этапе разработки;
  в репозитории нет автотеста, воспроизводящего эту проверку (там нет
  TensorFlow-окружения для сравнения).
- Итоговый размер `tempocnn_engine.exe` не измерен точно до сборки — оценка
  "десятки МБ" ориентировочная, зависит от того, что реально тянут за собой
  `librosa`/`numba` при заморозке PyInstaller.

## Проверка

**Автоматическая.** Существующий fengari-харнесс (51 проверка) обновляется в
местах, где матчит текст вывода движка и заголовок диалога (новая маркировка
`__ENGINE_EXIT__`, шкала `confidence` 0–1). Остальной сценарий — выбор item,
применение, отмена, ручной ввод, округление, метаданные, чистка файлов, защита
от двойного запуска — не меняется.

**Разовая офлайн-проверка конвертации.** До коммита ONNX-файла — прогнать
оригинальный `tempocnn` (Keras) и конвертированный ONNX на одном наборе
тестовых треков, сравнить BPM.

**Ручная в REAPER.** Тот же чек-лист, что и в
`2026-08-18-bpm-action-ux-design.md`, плюс явная сверка на треке
`Audiio_JustinMorgan_APlaceCalledHome` (истинный темп 113 BPM) — уже фигурировал
как проблемный случай для свёртки метрического уровня у Essentia, интересно
сравнить поведение TempoCNN.
