# TempoCNN BPM Detector для REAPER

ReaScript определяет темп аудиофайла через **TempoCNN (deeptemp_k16)**,
показывает найденный BPM для подтверждения и выставляет его как темп проекта. Темп всегда целый.
Метрический уровень не подгоняется: сколько услышал движок, столько и предлагается.
Самописный Lua-анализатор не используется.

## Состав

```text
Detect beat BPM and set project tempo.lua
engine/
  tempocnn_engine.exe    (~115 МБ)
  deeptemp_k16.onnx
  launch_engine.ps1
  run_engine.ps1
  src/tempocnn_engine.py    исходник движка (для воспроизводимой сборки)
docs/
  superpowers/specs/          дизайн-документы
  superpowers/plans/          планы реализации
dev/
  test/                       проверки скрипта вне REAPER
  model_conversion/           воспроизводимая сборка модели и exe
```

Lua-файл и папка `engine/` обязательны и должны сохранять эту структуру.

## Установка

1. В REAPER откройте `Actions` → `Show action list…`.
2. Нажмите `New action` → `Load ReaScript…`.
3. Выберите `Detect beat BPM and set project tempo.lua`.
4. При желании назначьте action хоткей или кнопку.

Если предыдущая версия уже загружена из того же файла, импортировать её повторно не нужно.

## Использование

1. Добавьте бит в проект.
2. Запустите **Detect beat BPM with TempoCNN and set project tempo**.
3. Скрипт сначала проверит BPM в метаданных и в имени файла. Если точной подсказки нет,
   он запустит локальный TempoCNN engine в фоновом процессе.
4. По окончании появится окно с найденным BPM. Enter применяет его, Cancel отменяет всё.

Во время анализа интерфейс REAPER остаётся доступным. Короткий launcher запускается через явный
системный путь Windows PowerShell и отделяет анализатор от процесса REAPER, а runner ограничивает
его работу 180 секундами.

Скрипт молчит до самого окна подтверждения: ReaScript console не открывается и не засоряется.
Сообщения появляются только при ошибке — обычным окном.

## Индикатор анализа

Пока идёт анализ, видно три вещи:

* небольшое окно с именем файла, бегущей полосой и счётчиком секунд;
* подпись стадии — `Запуск движка`, пока движок не отозвался, дальше `Анализ`;
* подсветка кнопки на тулбаре, если action на неё назначен.

Полоса именно бежит, а не заполняется: движок не сообщает промежуточный прогресс, и рисовать
проценты означало бы их выдумать.

Анализ отменяется клавишей Esc или закрытием окна — молча, без сообщений. Процесс движка при
этом доживает своё в фоне, а его результат подчищается при следующем запуске. Позиция item и
темп проекта не меняются.

## Какой item анализируется

Первое сработавшее правило выигрывает:

1. Ровно один выделенный audio item.
2. Выделено несколько — скрипт откажется работать: какой из них бит, он не угадывает.
3. Ничего не выделено — берётся item под edit-курсором. Если их несколько на разных треках,
   приоритет у выбранного трека.
4. Иначе — если в проекте ровно один audio item, берётся он.

Позиция мыши не используется: при запуске с кнопки тулбара курсор находится над этой кнопкой.

## Окно подтверждения

Одно поле с найденным BPM. Заголовок выглядит так:

```text
Detected 140 BPM (half 70 / double 280, conf 0.84)
```

Половинный и удвоенный варианты выписаны сразу, потому что метрический уровень — самая
ненадёжная догадка любого трекера. Нужен halftime — набираешь 70 и жмёшь Enter.

Вместо `conf` для точной подсказки стоит её источник: `metadata ID3:TBPM` или `filename`.

Введённое вручную число тоже округляется до целого: дробный темп проекта этому action не нужен.

Item никогда не двигается — меняется только темп проекта. Правка попадает в один undo-блок.

## Half-time и double-time

Один и тот же ритм может быть корректно описан как 70 или 140 BPM, и автоматически выбрать
верный уровень нельзя. Свёртка в фиксированное окно вида 55–110 обслуживает ровно один жанр,
а на всём остальном врёт вдвое: трек на 113 BPM она превращала в 56.

Поэтому свёртки нет. Показывается то, что услышал движок, а оба соседних уровня выписаны
в заголовке окна — переход на любой из них стоит одного набора числа.

## Временные файлы

Обмен с движком идёт через два файла в папке `engine/`:

* `bpm_job_<guid>.txt` — путь к анализируемому аудио, в UTF-8;
* `bpm_result_<guid>.txt` — вывод движка. Пока анализ идёт, рядом лежит `…txt.running`.

Обычно они удаляются сразу после чтения, но остаются, если анализ прерван — закрытием REAPER
или клавишей Escape, которая останавливает все фоновые ReaScript-циклы. Такие остатки молча
подчищаются при следующем запуске.

Повторный запуск во время идущего анализа отклоняется.

## Пути с кириллицей

Путь к аудио не передаётся командной строкой: он записывается в job-файл как UTF-8 и читается
оттуда. Командная строка на Windows — единственное место, где кириллица в пути гарантированно
портится, потому что `os.execute` в Lua идёт через ANSI-функции C runtime и переосмысляет
UTF-8-байты REAPER через системную кодовую страницу. По той же причине процесс запускается
через `reaper.ExecProcess`, а не `os.execute`: REAPER сам конвертирует команду в UTF-16.

Вывод движка декодируется как UTF-8, а при неудаче — как системная ANSI-кодировка: собранный
PyInstaller-ом exe запускает интерпретатор с изолированной конфигурацией, которая игнорирует
`PYTHONIOENCODING`, и пишет stdio в ANSI. Исходник движка при этом сам переключает потоки
на UTF-8, так что после пересборки exe сработает первая ветка.

Если движок не отозвался за 20 секунд (нет ни результата, ни `.running`-файла), скрипт
сообщает о неудачном запуске, не дожидаясь полного трёхминутного таймаута.

## Движок

Используется TempoCNN (`deeptemp_k16`, Hendrik Schreiber) — свёрточная сеть,
предсказывающая темп напрямую по мел-спектрограмме. Веса сконвертированы из
оригинального Keras-формата в ONNX и исполняются через `onnxruntime`, без
зависимости от TensorFlow в собранном движке. Работает локально, аудио никуда
не отправляется.

SHA-256 `tempocnn_engine.exe`:

```text
2D4EB0498903C3C4060A7169490BCBC6067E83A6229CF2984F6ABC426288CF32
```

SHA-256 `deeptemp_k16.onnx`:

```text
4D41FCC576C0B510DFB807A5A19BC04A1D77EDF6AF9341A9F7982B06F1B921C5
```

Приложенный exe собран из `engine/src/tempocnn_engine.py` до правки кодировки stdio (v2.0.1),
поэтому пересборка из текущего исходника даст другой SHA-256. Работу это не меняет: runner
декодирует вывод обеих сборок — см. «Пути с кириллицей».

Как воспроизвести сборку модели (.onnx) и exe-движка — `dev/model_conversion/README.md`.
